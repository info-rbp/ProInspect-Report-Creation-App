# Canonical Property Layout Integration

## Purpose

Phase 3 moves Property Layouts onto the canonical Areas & Components Catalogue. Property layouts no longer depend on Area or Component display-name inference to decide what a physical Area represents, which Components belong to it, or whether a Component is operational.

This phase deliberately does not rewrite historical Reports. Existing report snapshots keep the identities and evidence they were created with. New Property Layout Versions and new Reports carry explicit canonical references.

## Identity model

A Property has its own physical instances. Those instances are not the catalogue definitions themselves.

A Property-owned Area instance records:

- its own stable Property Area `id`;
- a user-facing display `name` that may be renamed without changing meaning;
- `canonicalAreaDefinitionId`;
- `canonicalAreaDefinitionVersion`; and
- Property context such as level, responsibility and notes.

A Property-owned Component instance records:

- its own stable Property Component `id` scoped to the Property Area;
- `canonicalComponentDefinitionId`;
- `canonicalComponentDefinitionVersion`;
- `canonicalAreaComponentRuleId`;
- `canonicalAreaComponentRuleVersion`;
- ordering and inclusion metadata; and
- the evidence default inherited when the Property layout snapshot was created.

This lets two bedrooms share the same canonical `bedroom` Area definition and the same canonical `walls` Component definition while retaining distinct Property Area and Component instance identities.

## Exact version binding

Property Layout Versions bind to:

- `proinspect-property-layout-catalogue`;
- catalogue contract version `1`;
- exact Area definition versions; and
- exact Component/rule versions.

Published catalogue definitions are immutable. A later catalogue change therefore creates a later definition version rather than silently changing the meaning of an existing Property Layout Version.

Where an existing residential Component needed broader commercial, industrial, retail or strata applicability, Phase 3 creates a later system Component version using the same stable Component identity. Residential version 1 remains unchanged for historical compatibility.

## Ten system Property Layout templates

Phase 3 preserves the ten existing user-facing template identities:

2. `res-house-4x2`

Every Area in every template now references an exact published Area definition and is populated from the exact Area-Component rule set. Components are no longer generated by scanning room labels.

## Expanded system catalogue

The Property Layout catalogue adds the missing domain coverage required by those templates.

### Residential and furnished

Added definitions include balcony/courtyard, storeroom, car bay, internal stairs/landing and furniture/included chattels. The furnished apartment template now has a dedicated furnishing/chattels Area rather than treating furniture as an informal note.

### Commercial office

Added Areas include external entry/façade, reception, open office, private office, meeting room, kitchenette, amenities, server/communications room, commercial storage, HVAC/mechanical services, electrical/lighting services, fire/safety systems and commercial parking.

### Retail and hospitality

Added Areas include shopfront/signage, sales area, POS/counter, display fixtures, retail storeroom, office, preparation area, amenities and external areas. Hospitality/restaurant property types additionally receive commercial-kitchen and coolroom/refrigeration Areas. Showrooms receive a showroom-floor Area.

### Warehouse and industrial

Added Areas include warehouse floor, loading area, roller doors, warehouse office, amenities, mezzanine, racking/storage, external yard, boundary fencing and car parking, with industrial electrical and safety service Areas.

### Strata common property

Added Areas include building entry, lobby/common hallways, lifts/lift lobby, stairwells, common amenities, common car park, common storage, external walls/grounds, plant/services and fire/safety systems. Property responsibility is recorded as common property rather than being inferred from wording.

### Specialist property types

Physical Property Type controls specialist Areas directly:

- `medical_consulting` adds consulting and treatment rooms;
- `childcare` adds activity rooms, sleep room and outdoor play area;
- `retirement_supported` adds accessibility/resident-safety checks;
- `hospitality` and `restaurant_cafe` add commercial kitchen and refrigeration Areas; and
- `showroom` adds showroom-floor fixtures.

These selections use canonical classification fields, not text matching.

## Property Workspace

The live **Layout & Areas** tab now uses the canonical Property Layout editor.

The editor:

- filters system templates by Property Use and Physical Property Type;
- applies a template as a new immutable layout snapshot;
- shows each Property Area's exact canonical Area version;
- shows how many canonical Components are populated in each Area;
- allows the Property display label to be renamed independently of canonical identity;
- loads published agency-defined Areas from the Catalogue API;
- filters those Areas by Property applicability;
- creates new Property Area instances from an exact published Area version; and
- copies another Property layout while regenerating Property instance IDs and retaining canonical definition IDs.

Free-text display names are therefore presentation data, not schema keys.

## Legacy Property migration

Known template-backed Property layouts are migrated without comparing Area names.

The migration uses:

1. the persisted `layoutTemplateId`;
2. the canonical version of that template; and
3. ordered typed Area slots (`RoomType`) to retain the existing Property Area instance where a deterministic slot exists.

A renamed Kitchen can therefore remain called anything the agency wants while still becoming `canonicalAreaDefinitionId = kitchen`.

If a legacy Property contains custom Areas that cannot be deterministically mapped, those Areas remain explicitly unmapped for human review. Phase 3 does not guess an Area definition from the label. This is intentional. An explicit unresolved mapping is safer than a confident-looking false identity.

Migration creates a new Property Layout Version. It does not mutate historical layout snapshots or historical Reports.

## Report seeding

New Report Areas now preserve:

- the Property Area instance ID;
- canonical Area definition ID/version; and
- the Property Layout Version used to create the Report.

New Report Components preserve:

- the Property Component instance ID;
- canonical Component definition ID/version; and
- canonical Area-Component rule ID/version.

Operational state is determined from the exact Component definition category. Component display names no longer determine whether something is testable or operational.

A legacy fallback remains only for genuinely unmapped layouts. It uses the stored `RoomType` enum and exact canonical Area mappings. It never scans the Area name.

## Agency-defined catalogue records

Agency-defined Areas and Components continue to use the server-backed Catalogue administration workflow.

A Property can use an agency Area only after that exact Area version is published and immutable. The Property Layout editor then stores the exact Area version and every exact Component/rule reference supplied by the published Area. Reports retain those IDs even when the system package does not know the agency-defined Component locally.

## Authority boundary after Phase 3

After Phase 3:

- the Catalogue owns Area/Component vocabulary and reusable Area-Component rules;
- a Property Layout Version owns the physical Property instances and exact catalogue bindings;
- a Report owns an inspection-time snapshot of those Property instances;
- historical Reports remain immutable; and
- display wording does not establish identity.

The next phases remain separate:

- Report Template composition from catalogue references rather than cloned arrays;
- server-authoritative Report structure resolution from Property Layout Version + published Inspection Template Version + Catalogue; and
- Historical Report Intelligence, Comparison/QC, Maintenance and pricing migration onto the same canonical identities.
